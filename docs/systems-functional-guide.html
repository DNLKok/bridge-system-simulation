What systems.py Does

A functional guide to how bidding agreements become decisions

Purpose

systems.py is the bridge between a bidding agreement and a call in an auction. It loads a system's rules, checks them against the current hand and auction, and returns the first applicable legal call. The agreement itself lives primarily in TOML files, so different systems can combine reusable modules without putting each bidding convention in Python code.

From files to a usable system

  1. A system manifest names its modules in priority order and says what to do if none applies.
  2. Each module contains ordered rules. A rule describes when it applies and either one call or a preference list of calls.
  3. load_system() reads the manifest and assembles the referenced modules. It checks that each module's ID and version agree with the manifest, and that the files describe a supported system. load_module() reads and checks a module on its own.

This makes a system a composition of agreements: a system author can reuse a module, change module order, or substitute another module while keeping the remaining modules intact. Older single-system TOML files are also accepted and treated as a one-rule system.

How a call is chosen

The caller provides the current seat's hand facts, the auction so far, the calls that are legal now, the dealer, and vulnerability. Together these describe the decision being made; they do not themselves specify a bidding agreement.

  1. The system checks its modules in manifest order. Earlier modules have priority over later ones.
  2. Within each module, rules are checked in file order. A rule can depend on hand facts such as HCP, shape, suit length or suit HCP, and on auction facts such as whether the seat is at passout or no contract bid has yet occurred.
  3. When a rule applies, its preferred calls are considered in order. The first call that is legal in the current auction is selected. If no module provides a call, the system's configured fallback is used.

The fallback may be a regular call (often pass) or the explicit OUT_OF_BOOK result. The latter means the system has no defined answer for this situation; it is not itself a bridge call. choose_call() also guards against returning an illegal call.

In short: system order determines which agreement gets the first say; rule and call order determine its preferred legal action; the fallback handles everything left over.

How it connects to the rest of the workspace

Running an auction

auction.run_auction() manages turn-taking and legal calls. At each turn it builds a decision context and asks the relevant partnership's system for a call. It records an ordinary call and continues; if the system returns OUT_OF_BOOK, the auction runner reports that it needs a separate recommendation rather than treating that result as a bid.

Hand information

The context uses shared bridge facts from model.py, including the hand profile, seat, and auction calls. deals.py supplies profiles from card hands; when cards are available, it can provide per-suit HCP as well as total HCP and shape. A rule requiring information that a supplied profile does not contain fails explicitly rather than guessing.

Helping with a partial auction

auction_assistant.py asks the system what hand conditions would explain each observed call by a partner or opponent. dealer_call_condition() turns rule conditions into Dealer expressions, allowing the assistant to generate deals compatible with the auction. If a call conflicts with the configured agreement, the assistant reports the inconsistency.

Handling an undefined situation

model_assistant.py loads the same system and checks whether the current position has a defined call. It uses the system's call when one exists; when the system explicitly reports out of book, it can rate legal alternatives using generated deals and double-dummy results. This is a separate recommendation workflow, not an extra bidding rule inside systems.py.

What this file does not do

systems.py does not generate deals, run the auction to completion, score contracts, or decide which call is strategically best outside the agreements it loads. It interprets configured rules and selects a legal action; the surrounding auction and assistant code owns those other tasks.
